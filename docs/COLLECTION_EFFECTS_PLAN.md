# 수집품 능력 시스템 기획안

상태: **Claude 1차 리뷰 완료·소유자 결정 대기 — 구현 금지**
대상 아이디어: Telegram `telegram-415676354`
목표 출시: **iOS 최초 출시 후 두 번째 업데이트 + 그와 짝을 이루는 Android 동시 버전**
선행 출시: iOS 첫 번째 업데이트는 현재 심사 중인 Android 버전과 기능을 맞추는 데만 사용한다.

## 1. 목적

팬트리 항아리와 배지가 단순 전시품에 머물지 않고 다음 순환을 만들게 한다.

> 퍼즐 플레이 → 수집품 획득·구매 → 능력 선택 → 플레이 중 효과 체감 → 더 수집하고 싶어짐

다만 수집품이 없으면 퍼즐 진행이 불가능하거나, 결제한 이용자만 유리한 구조가 되어서는 안 된다. 능력은 **보조와 보상의 개성**을 만들되 퍼즐의 정답·진행·기본 보상은 보장한다.

## 2. 이번 버전의 제품 원칙

1. **전시와 능력을 분리한다.**
   - `홈에 전시`: 외형 선택. 능력과 무관하다.
   - `선반에서 선택`: 기존처럼 선반 외형만 바꾼다. 능력과 무관하다.
   - `효과 활성화`: 획득한 항아리 중 전역 효과 항아리 하나를 별도로 고른다.
   - `배지 능력 장착`: 전체 게임에 적용할 배지 하나를 고른다.
   - 홈에 보이는 항아리·배지와 실제 능력 항목이 달라도 정상이다.

2. **항아리와 배지의 역할을 다르게 한다.**
   - 항아리: 스푼 보상과 보상 기회에만 관여한다.
   - 배지: 힌트·실수 보호·플레이 편의에만 관여한다.
   - 시너지: 정해진 항아리와 배지 조합에만 작은 추가 효과를 준다.

3. **수치는 정확히 공개한다.**
   - “보상이 좋아져요”가 아니라 `완료 시 12% 확률로 스푼 +1`처럼 표시한다.
   - 발동 조건, 적용 모드, 일일 상한을 같은 화면에서 볼 수 있어야 한다.

4. **효과가 발동하면 반드시 보인다.**
   - 기본 보상과 수집품 보상을 합계만으로 보여주지 않는다.
   - 항아리 그림·이름과 함께 별도 보상 행 및 짧은 애니메이션을 보여준다.

5. **중첩은 덧셈만 사용하고 상한을 둔다.**
   - 배수 중첩이나 무한 루프를 금지한다.
   - 항아리 효과, 배지 효과, 시너지 효과를 각각 한 번만 평가한다.

6. **양 플랫폼은 같은 규칙과 데이터를 사용한다.**
   - Android/iOS는 동일한 웹 게임 데이터와 저장 마이그레이션을 사용한다.
   - 어느 한쪽에서만 먼저 능력을 활성화하지 않는다.

## 3. 권장 장착 구조

### 3.1 항아리: 기존 전시 선택과 별도의 전역 효과 슬롯

현재 선반별 `equippedJars`는 미관 선택으로 그대로 보존한다. 이를 능력으로 재해석하지 않고, 획득한 항아리 중 하나를 전역 `activeJarId`로 고르는 별도 효과 슬롯을 추가한다.

- `equippedJars`: 선반에서 보이는 항아리. 기존 의미와 저장을 유지한다.
- `featuredJarId`: 홈에 전시하는 항아리. 기존 의미를 유지한다.
- `activeJarId`: 보상 효과를 주는 항아리 하나. 신규이며 명시적 동의 후에만 설정한다.
- 기존 이용자의 미관 선택을 자동으로 능력 선택으로 전환하지 않는다.
- 최초 진입 시 효과 항아리를 고르도록 안내하되, 선택 전에도 기본 보상과 플레이는 그대로 유지한다.
- V1 효과는 스테이지/선반 소속이 아니라 항아리 자체의 `적용 모드` 규칙으로 평가한다.
- 타임어택은 생성 퍼즐에 시즌 선반이 없으므로 V1 항아리 효과 대상에서 제외한다.

장점:

- 21개 시즌 선반과 11개 항아리 선반을 억지로 대응시키지 않아도 된다.
- 기존 이용자가 예쁘다고 골랐던 항아리의 의미가 갑자기 바뀌지 않는다.
- 모든 화면에서 `현재 효과 항아리` 하나만 설명하면 되어 이해하기 쉽다.

### 3.2 배지: 능력 슬롯 하나 추가

현재 `featuredBadgeId`는 홈 전시용이다. 능력용으로 별도 `activeBadgeId`를 추가한다.

- 획득한 배지 중 하나만 능력 장착 가능.
- 홈 전시 배지와 능력 장착 배지는 독립적.
- 기존 이용자는 첫 보유 배지를 기본 장착하거나, 첫 진입 시 선택 안내를 한 번 보여준다.

## 4. 효과 체계

### 4.1 항아리 효과: 스푼 보상 전용

66개 항아리에 66개의 완전히 다른 규칙을 만들지 않는다. **11개 항아리 카테고리별 효과 계열**을 만들고, 같은 카테고리의 항아리는 희귀도·가격에 따라 강도와 조건이 달라진다. 이 분류는 시즌 선반 소속과 무관하다.

초기 효과 계열 후보:

| 선반 계열 | 적용 대상 | 효과 예시 |
| --- | --- | --- |
| 잼·과일 | 일반 퍼즐 | 완료 시 일정 확률로 스푼 +1 |
| 꿀·시럽 | 오늘의 그림 | 일일 최초 완료 보너스에 스푼 추가 |
| 허브·꽃 | 큰 퍼즐 | 10×10 이상 완료 시 추가 스푼 기회 |
| 향신료·차 | 타임어택 | 완주 보상 또는 신기록 보상에 소량 추가 |
| 나머지 선반 | 재도전·연속 완료·특정 크기 | 같은 보상 역할 안에서 조건만 차별화 |

확정 전 수치 후보이며 경제 시뮬레이션 후 조정한다:

| 등급 | 후보 효과 | 안전장치 |
| --- | --- | --- |
| Starter | 효과 없음 또는 튜토리얼용 3%/+1 | 구매 없이 기본 플레이 보장 |
| Common | 6~8% 확률로 +1 | 하루 최대 +2 |
| Rare | 9~11% 확률로 +1 | 하루 최대 +3 |
| Special | 12~14% 확률로 +1 | 하루 최대 +4 |
| Luxury | 15% 확률로 +1 또는 8% 확률로 +2 | 하루 최대 +5 |

확률만 사용하면 운이 나쁜 이용자가 효과를 전혀 체감하지 못할 수 있다. 권장안은 **실패 누적 보정**이다.

- 연속 미발동 횟수를 항아리별이 아니라 계정 공통의 `jarEffectPity`로 저장한다.
- 예: 5회 연속 미발동이면 다음 적격 완료에서 +1 보장.
- 발동하면 누적값을 0으로 되돌린다.
- 상세 화면에는 `다음 보너스 보장까지 2회`처럼 표시할 수 있다.

정확한 확률·보정 횟수·일일 상한은 500개 퍼즐 전체 경로와 7일/30일 플레이 모델을 돌린 뒤 확정한다.

### 4.2 배지 효과: 플레이 보조 전용

12개 배지는 **4개 효과 계열 × 3단계**로 구성하는 것을 권장한다. 배지는 플레이로만 획득하므로 항아리보다 조금 더 명확한 편의를 줄 수 있다.

| 계열 | 1단계 | 2단계 | 3단계 |
| --- | --- | --- | --- |
| 힌트 절약 | 첫 유료 힌트 비용 -1 | 힌트 비용 할인 강화 | 일일 1회 힌트 비용 전액 보존 |
| 힌트 획득 | 적격 완료 시 낮은 확률로 힌트 조각 | 확률 상승 | 일정 횟수 후 1회 보장 |
| 실수 보호 | 일일 1회 오입력 경고 | 보호 횟수 증가 | 큰 퍼즐에 추가 보호 |
| 시간 집중 | 타임어택 시작 시 소량 여유 | 여유 증가 | 신기록 도전 시 추가 보조 |

주의:

- 정답 셀을 자동으로 많이 공개하거나 퍼즐을 자동 완성하지 않는다.
- 힌트 소비가 스푼 경제의 일부이므로 할인·환급에는 일일 상한을 둔다.
- 배지 하나만 활성화되므로 복잡한 능력 중첩을 피한다.

### 4.3 시너지

V1에서 모든 조합을 만들지 않는다. **이름과 테마가 자연스러운 6개 조합만** 큐레이션한다.

예시:

| 조합 | 작은 시너지 예시 |
| --- | --- |
| 딸기 잼 + 첫 선반 배지 | 항아리 보너스 발동 시 10% 확률로 힌트 조각 1개 |
| 라벤더 꿀 + 집중 배지 | 오늘의 그림 첫 플레이에서 힌트 비용 -1 |
| 향신료 항아리 + 시간 배지 | 타임어택 신기록 보너스 +1, 일 1회 |

규칙:

- 시너지는 기본 효과를 대체하지 않고 작은 부가 효과만 준다.
- 곱연산 금지, 하루 최대 발동 횟수 표시.
- 보유하지 않은 조합도 팬트리 상세 화면에서 흐리게 미리 보여 수집 목표를 만든다.
- 경제 검증이 불충분하면 V1에서는 화면과 데이터 구조만 준비하고 실제 시너지는 다음 버전으로 미룬다.

## 5. 이용자가 실제로 보게 되는 UX

### 5.1 최초 안내

기능 업데이트 후 처음 홈에 들어오면 기존 Pip과 기존 말풍선을 사용해 2단계로만 안내한다.

1. `이제 팬트리 항아리를 고르면 퍼즐 보너스를 받을 수 있어요!`
2. `배지 하나를 능력으로 장착하면 힌트와 플레이에 도움을 받을 수 있어요.`

버튼:

- `효과 보러 가기`
- `나중에`

설정의 `Pip의 가이드`에서 다시 볼 수 있다.

### 5.2 팬트리 항아리 상세

상세 카드 안을 세 구역으로 구분한다.

1. **수집 정보**: 이름, 등급, 가격, 보유 여부.
2. **선반 효과**:
   - `일반 퍼즐 완료 시 12% 확률로 스푼 +1`
   - `오늘 1/4회 발동`
   - `보너스 보장까지 2회`
3. **선택 상태**:
   - `이 선반에서 선택하기`
   - 선택 후 `선반 효과 사용 중 ✓`
   - 별도 버튼 `홈에 전시하기`

`선반에서 선택`과 `홈에 전시`는 색·아이콘·설명까지 다르게 표현한다.

### 5.3 배지 상세

- `능력`: 정확한 효과와 일일 상한.
- `능력 장착하기` / `능력 사용 중 ✓`.
- 별도 `홈에 전시하기`.
- 시너지 대상 항아리가 있으면 `함께 사용하면` 영역에 조합을 보여준다.

### 5.4 플레이 진입 전

퍼즐 제목 아래에 한 줄짜리 `오늘의 활성 효과`를 표시한다.

예:

`🍓 딸기 잼: 완료 보너스 +1 기회   🏅 첫 선반 배지: 첫 힌트 -1`

- 탭하면 상세 설명을 연다.
- 작은 화면에서 한 줄을 넘으면 가로 스크롤하지 않고 2행으로 줄바꿈한다.
- 플레이 보드 공간을 줄이지 않도록 접을 수 있다.

### 5.5 플레이 중

- 항아리 아이콘은 보상과 관계없는 동안 계속 흔들거나 빛나지 않는다.
- 배지 효과가 힌트에 적용되면 힌트 버튼 옆에 작은 배지 아이콘과 할인 값을 표시한다.
- 실수 보호가 남아 있으면 `보호 1회`를 짧게 표시한다.
- 핵심 퍼즐판보다 수집 효과 UI가 더 눈에 띄지 않게 한다.

### 5.6 완료 보상 — 가장 중요한 체감 화면

현재 합산 보상을 다음처럼 원장 형태로 분리한다.

```text
퍼즐 완성!

기본 퍼즐 보상                 +4 🥄
오늘의 그림 보너스             +8 🥄
🍓 딸기 잼 · 선반 효과         +1 🥄
────────────────────────────
총 획득                        +13 🥄
```

표현 규칙:

- 기본 보상은 기존 색을 유지한다.
- 항아리 추가 보상 행은 항아리 실제 아트, 이름, `선반 효과` 라벨과 금색 강조를 사용한다.
- 추가 스푼이 총 스푼 수로 이동하는 0.6~0.9초 애니메이션을 한 번만 보여준다.
- 기존 Pip 말풍선을 잠깐 `딸기 잼 덕분에 스푼을 하나 더 찾았어요!`로 바꾼 뒤 원래 대사로 되돌린다.
- 감소된 모션 설정에서는 숫자와 강조만 즉시 표시한다.
- 발동하지 않은 확률 효과는 완료 화면에서 실패 메시지를 보여주지 않는다.

배지 효과가 발동한 경우에는 보상 아래 별도 행으로 보여준다.

```text
🏅 배지 효과   힌트 비용 1 스푼을 아꼈어요
```

이 구분 덕분에 이용자는 `기본으로 받은 것`과 `내가 선택한 수집품 덕분에 더 받은 것`을 즉시 이해한다.

### 5.7 홈 화면

- 홈에 전시한 항아리·배지에는 기존 외형을 유지한다.
- 능력까지 활성화된 경우 작은 `효과 사용 중` 표시만 추가한다.
- 홈 전시품과 능력품이 다르면 두 개를 겹쳐 보여주지 않는다.
- 홈의 Pip 말풍선은 가끔 `현재 선택한 딸기 잼이 일반 퍼즐 보너스를 도와줘요.`처럼 설명하되 반복 빈도를 제한한다.

## 6. 경제 안전장치

현재 기본 경제를 먼저 고정한 뒤 추가 기대값을 계산한다.

- 일반 퍼즐 보상: 5×5 `2`, 8×8 `4`, 10×10 `6`, 12×12 `10`, 15×15 `22`, 18×18 `30`.
- 오늘의 그림 보너스 `8`, 로그인 보너스 `3`.
- 타임어택 보상 `10/18/30/45`, 신기록 `12`.
- 인앱상품 `150`, `500` 스푼.

### 6.1 추가 보상 도입과 기존 공급량 재조정

수집품 효과로 스푼을 새로 공급하면서 데일리 보너스와 스푼 벌러 가기 보상을 그대로 두면 총 공급량이 증가한다. 그러면 항아리 구매 속도가 빨라지고, 스푼 부족을 해소하는 인앱상품의 필요성도 낮아질 수 있다. 따라서 아래 항목을 **하나의 스푼 공급 예산**으로 함께 시뮬레이션한다.

- 일반 퍼즐 기본 보상.
- 오늘의 그림/데일리 보너스.
- 스푼 벌러 가기 최초 완료 및 재도전 보상.
- 로그인·스테이지·타임어택 보상.
- 항아리 추가 보상과 시너지 추가 보상.
- 배지의 힌트 할인·보존으로 절약되는 스푼까지 포함한 간접 공급 효과.

권장 원칙은 **기본 퍼즐 보상은 유지하고, 반복적으로 지급되는 데일리·스푼 벌기 예산부터 조정 후보로 삼는 것**이다. 퍼즐의 기본 보상을 줄이면 아직 수집품이 없는 신규 이용자가 가장 크게 손해 보기 때문이다.

검토할 세 가지 안:

| 안 | 기존 보상 | 수집품 보상 | 평가 |
| --- | --- | --- | --- |
| A. 추가형 | 모두 유지 | 그대로 추가 | 체감은 좋지만 인플레이션 위험이 가장 큼 |
| B. 재배분형 | 데일리·스푼 벌기 일부 축소 | 줄인 예산을 수집품 발동 보상으로 이동 | **권장 검토안**. 총량을 유지하면서 수집 가치를 보여줌 |
| C. 상한형 | 모두 유지 | 일일 수집품 보너스를 매우 낮게 제한 | 안전하지만 능력 강화 체감이 약할 수 있음 |

재배분형의 초기 시뮬레이션 예시이며 확정 수치가 아니다:

- 오늘의 그림 보너스 `8 → 6` 후보.
- 줄어든 `2`는 활성 항아리의 보너스 기회·보장 게이지에 배정.
- 스푼 벌러 가기는 최초 완료의 고정 보상을 소폭 줄이거나, 재도전 보상/일일 횟수 쪽을 먼저 조정한다.
- 가장 약한 Starter 항아리에도 데일리에서 체감 가능한 최소 효과를 주어 신규 이용자의 실질 보상이 갑자기 줄지 않게 한다.
- 운이 나쁜 이용자가 과거보다 적게 받는 기간이 길어지지 않도록 실패 누적 보정을 적용한다.

중요한 UX 원칙:

- 이용자에게 기존 `+8`을 `+6`으로 줄였다는 인상만 주고 항아리 발동은 드물게 보이게 해서는 안 된다.
- 동일한 평균 지급량을 재배분하더라도 첫 며칠 안에 항아리 추가 보상을 반드시 체험하게 한다.
- 완료 화면에는 `기본/데일리 보상`과 `수집품 추가 보상`을 별도 행으로 보여 강화 가치를 명확히 한다.
- 효과가 발동하지 않은 날에도 상세 화면의 보장 게이지가 진행되어 “보상이 사라졌다”가 아니라 “다음 추가 보상에 가까워졌다”고 이해할 수 있어야 한다.
- 기존 이용자에게는 기능 업데이트 최초 진입 시 `일부 보상이 선반 효과로 이동했어요. 총 보상 균형은 유지돼요.`처럼 투명하게 안내한다. 실제 시뮬레이션이 이를 증명하지 못하면 이 문구를 사용하지 않는다.

출시 전 비교 기준:

- 수집품이 거의 없는 신규 이용자의 7일 총 획득량은 현행 대비 **-5% 미만**으로 떨어지지 않는다.
- 중간 진행 이용자의 30일 총 획득량은 현행 대비 대략 **-3%~+8%** 범위에서 목표를 정한다.
- 최강 조합의 30일 총 획득량도 현행 대비 **+15%**를 넘지 않는다.
- 수집품 강화에 따라 `고정 보상 ↓ / 선택 효과 보상 ↑`가 보이되, 확률 운 때문에 장기간 현행보다 크게 손해 보는 계정이 없어야 한다.
- 항아리 구매 완료 예상 기간과 150/500 스푼 상품의 상대적 가치가 현행에서 과도하게 짧아지거나 무의미해지지 않는다.

최종 조정 대상은 시뮬레이션 결과로 결정한다. 데일리와 스푼 벌기 둘을 동시에 크게 줄이지 말고, 한 번에 한 축씩 바꾼 결과를 비교한다.

출시 기준 후보:

- 수집품으로 늘어나는 월간 무료 스푼 기대값은 동일 플레이 기준 기존 획득량의 **8~12% 이내**.
- 가장 강한 조합도 **15%를 넘지 않음**.
- 항아리 구매 비용 회수 기간이 지나치게 짧아지지 않게 한다.
- 수집품 보너스로 다음 항아리를 무한히 빠르게 구매하는 순환을 일일 상한으로 막는다.
- 결제하지 않아도 모든 효과 계열을 낮은 단계에서 경험할 수 있어야 한다.
- 확률 결과는 클라이언트 재시작·시계 변경으로 반복 추첨할 수 없게 완료 원장과 함께 저장한다.

필수 시뮬레이션:

1. 신규 이용자 7일: 하루 3/10/20 퍼즐.
2. 기존 이용자 30일: 작은 퍼즐 중심/큰 퍼즐 중심.
3. 무결제/150 스푼 구매/500 스푼 구매.
4. 최약·중간·최강 장착 조합.
5. 일반 퍼즐/오늘의 그림/스푼 벌러 가기/타임어택별 기대 획득량.
6. 현행 경제/A 추가형/B 재배분형/C 상한형의 7일·30일 총 공급량 비교.
7. 확률 하위 10% 이용자가 받는 보상량과 실패 누적 보정 적용 후 최저 보상량 비교.

### 12.1 가장 먼저 지적해야 할 구조적 문제

§3.1은 "퍼즐이 속한 스테이지와 연결된 팬트리 선반"이라는 단일 개념을 전제로 하지만, 실제 코드에는 카운트가 서로 다른 **세 개의 독립된 선반/팩 분류 체계**가 이미 존재한다.

| 체계 | 파일 | 개수 | 용도 |
|---|---|---|---|
| 팩(Pack) | `packs.js` | 5개 | 언락 게이팅 단위 |
| 시즌 선반(Season Shelf) | `seasonShelves.js` | **21개** | 배지·스테이지 그룹핑 (`shelf-pips-first` 등) |
| 항아리 선반(Jar Shelf) | `pantryJars.js` | **11개** | 팬트리 구매 카테고리 (`jam`, `honey` 등) |

세 체계는 이름 규칙도 개수도 다르다(5 vs 21 vs 11, 정수배 관계도 아님). §4.1의 "잼·과일", "꿀·시럽" 효과 계열은 항아리 선반(11개) 기준인데, 퍼즐이 실제로 "속한" 것은 시즌 선반(21개)이다. 이 둘을 잇는 매핑 테이블은 코드에도 문서에도 없다. 이는 이 기획의 핵심 트리거 로직이 아직 정의되지 않았다는 뜻이다.

더 심각한 것은 **타임어택**이다. `randomPuzzle.js`의 타임어택 퍼즐은 `packId: "time-attack"`, `generated: true`로 매 라운드 절차적으로 생성된다. `seasonShelves.js`의 `shelfIdByPuzzleId` 맵은 저작된 `puzzles.js`로만 구축되므로, 타임어택 생성 퍼즐은 시즌 선반 소속이 아예 없다. §3.1의 "타임어택: 선택된 퍼즐이 속한 선반의 항아리를 사용한다"는 **참조할 선반 자체가 데이터상 존재하지 않아 그대로는 구현 불가능**하다. 크기별 고정 매핑 등 별도 규칙 설계가 필요하다.

### 12.2 요청 집중 항목별 반박

**A. 경제 인플레이션**
- §6 기준 수치(5×5=2, 8×8=4…, 데일리 8, 로그인 3, 타임어택 10/18/30/45+12, IAP 150/500)는 `economyConfig.js`와 정확히 일치한다 — 이 부분은 최신 상태를 잘 반영했다.
- 그러나 §6 표는 "일반 퍼즐 보상"을 `PUZZLE_REWARD_BY_SIZE[size]`와 동일시하는데, 그 상수는 실제로 **오늘의 그림 경로**(`spoonRunRewards.js:18`)에서만 쓰인다. 일반 퍼즐 완료 시 실제 지급액은 `puzzle.reward`라는 **퍼즐별 개별 저작 필드**(`puzzleView.js:62,71`)이며, 실제 예시(5×5 `pips-first-shelf-pip-face-1`)는 `reward: 3`으로 테이블 값 `2`와 다르다. 경제 시뮬레이션을 §6 표 기준으로 돌리면 처음부터 틀린 입력값으로 시작한다.
- 부가로 `stageBonus`가 `packs.js`(40/80…), `seasonShelves.js`(50/30/30/25…), `economyConfig.STAGE_BONUS_BY_SIZE`(40/80/130…) 세 곳에 서로 다른 값으로 흩어져 있다. 시뮬레이션 전에 "무엇이 진짜 라이브 값인가" 코드 감사가 선행돼야 한다.

**B. 기존 저장 호환성**
- `equippedJars`/`featuredJarId`/`featuredBadgeId` 필드는 이미 `save.js`에 존재해 구조적으로는 무난하다.
- 다만 **의미 변경(semantic drift)** 리스크가 있다. 현재 `equipped` 항아리는 "선반 퍼즐 플레이 중 보이는 병"이라는 순수 미관 선택이다(효과 없음, `pantryView.js:224`). 기존 이용자는 예쁜 병을 아무 고민 없이 골라뒀을 것이다. 기획 적용 순간 그 미관 선택이 스푼 보상률을 결정하게 된다. §3.1의 "미선택 선반은 starter 자동 선택"은 *미선택* 케이스만 방어하고, "이미 저가치 항아리를 미관상 equip해 둔" 케이스는 방어하지 않는다. §5.1의 2단계 툴팁만으로 이 전환을 충분히 알릴 수 있을지 의문 — 명시적 재점검 유도가 필요하다.

**C. 전시(featured)와 능력(equipped/active) 혼동**
- 항아리는 이미 "구매→equip(선반 선택)→feature(홈 전시)" 2버튼 UI가 라이브 상태다(`pantryView.js` 상세 패널). 능력화는 기존 패턴의 의미 재활용이라 상대적으로 저위험이다.
- 배지는 다르다. 현재 `featuredBadgeId`(홈 전시)만 존재하고 "장착/equip" 개념 자체가 코드에 없다. 배지의 전시-능력 분리는 이용자가 한 번도 본 적 없는 완전히 새로운 상호작용이며, 항아리처럼 "검증된 패턴 재사용"이라는 안전판이 없다. 두 케이스를 같은 난이도로 취급하면 안 된다.
- §5.7의 "겹쳐 보이지 않게" 규칙은 두 슬롯이 다를 때 정보가 한 화면에 동시에 안 보인다는 뜻이라 오히려 혼란 원인이 될 수 있다.

**D. 네 가지 게임 경로의 항아리 적용 규칙**
- 문서가 내적으로 불일치한다. §1·§9·§10 질문1은 "네 가지 경로"라 쓰는데 §3.1 규칙은 "일반 퍼즐/스푼 벌러 가기/타임어택" 세 가지만 명시한다. 오늘의 그림과 다시 풀기는 이미 서로 다른 완료 기록·리워드 경로(`recordDailyComplete` vs `replayPicked`)로 분리돼 있으므로, 항아리 활성화 규칙에서 이 둘을 하나로 묶어도 되는지 별도 명시가 필요하다.
- 타임어택은 12.1에서 지적한 대로 규칙 자체가 미완성이다.
- 일반 퍼즐/다시 풀기는 시즌 선반(21개)까지는 구할 수 있으나, 이를 항아리 선반(11개)으로 변환하는 매핑이 없다. 이 매핑표 설계·밸런싱은 Phase A("이번 주 기획 확정") 범위에 언급돼 있지 않다.

**E. 시너지를 V1에 포함할지**
- §11의 "데이터·UI만 준비, 다음 버전 활성화" 권장안에 동의한다. 시너지는 "항아리(11 선반 중 1) × 배지(12개 중 1)" 조합에 의존하므로, 위 매핑 문제의 하위 종속 작업이다. 매핑이 먼저 확정돼야 "자연스러운 조합"을 고를 수 있다.

### 12.3 §10 검토 질문 답변 (문서에 12개 항목이 있어 전부 답함)

1. **선반별 항아리 자동 활성화가 네 게임 경로에서 일관되게 설명 가능한가?** 아니요. "3규칙 vs 4경로" 불일치가 있고, 타임어택은 매핑 대상 선반이 데이터상 존재하지 않는다.
2. **`featured`와 `equipped/active` 분리가 혼동 없이 가능한가?** 항아리는 가능(기존 패턴 재사용), 배지는 신규 UX라 별도 검증 필요 — 같은 난이도로 취급 금지.
3. **확률 + 실패 누적 보정이 단순 확률/고정 횟수보다 나은가?** 설계 원칙상 낫다. 다만 "계정 공통 `jarEffectPity`"는 항아리마다 확률이 달라(6~15%) 자주 갈아끼우는 유저에게 "보장까지 N회"의 의미가 모호해질 수 있다. 계정 공통 vs 선반별 피티를 재확인할 것.
4. **11개 효과 계열로 66개 항아리가 충분히 개성 있어 보이는가?** 판단 이전에 "11 항아리선반 ↔ 21 시즌선반" 관계 정의가 선행돼야 한다. §4.1 표는 선반과 무관한 축(퍼즐 유형)으로 짜여 있어 선반 축으로 재정리가 필요하다.
5. **배지 효과가 힌트 소비·결제 동기를 지나치게 낮추지 않는가?** 힌트 경제는 Step 20/21에서 막 재조정됐다. 배지 3단계 "힌트 비용 전액 보존"이 이를 무력화할 위험이 있음. 힌트 매출 감소 상한 등 정량 기준이 §6에 없다.
6. **재배분형 vs 유지, 어느 쪽이 안전한가?** 재배분형(B)에 동의하나, "일반 퍼즐 보상은 유지"라는 약속이 12.2-A 문제(퍼즐별 개별 reward) 때문에 실효성이 제한적 — 기준 자체를 재정의해야 함.
7. **재배분형에서 신규/확률 하위 이용자 보호가 충분한가?** 방향은 합리적이나 검증이 시뮬레이션 의존. 입력값(§6 표)이 부정확하면 보호 기준도 무의미 — `puzzle.reward` 실제 분포 추출이 선행 작업.
8. **시너지 6개를 V1에 넣을 가치가 있는가?** 없음. 매핑 미해결 상태에서 조합 확정은 순서가 거꾸로. §11 "다음 버전" 권장안에 동의.
9. **완료 보상 원장·Pip 말풍선이 가치를 충분히 전달하는가?** UX 설계는 꼼꼼하나, "기본 퍼즐 보상 +4" 같은 고정 라벨 예시가 실제로는 퍼즐마다 다른 값이 들어가야 하므로 문구 템플릿 재검증 필요.
10. **보상 중복·저장 롤백·날짜 조작·오프라인 위험이 빠진 게 없는가?** 빠졌다. 앱은 완전 클라이언트 로컬 저장 구조로 서버 검증이 없다. 존재하는 방지책은 "동일 퍼즐 재완료 시 0 지급" 수준이며, `jarEffectPity`나 일일 상한처럼 날짜에 의존하는 신규 상태값은 기기 시계 조작에 노출된다(`getDailyDateKey()`가 `new Date()` 기반). 서버 없는 구조에서 "날짜 조작 방지"는 지키기 어려운 약속이므로 요구 수준을 현실화하거나 서버 검증을 로드맵에 별도로 얹어야 한다.
11. **예상 영향 파일과 테스트 범위를 제시할 수 있는가?** 가능. `save.js`(마이그레이션/activeBadgeId/pity), `pantryJars.js`+신규 `jarEffects.js`, `badges.js`+신규 `badgeEffects.js`, 신규 `collectionSynergies.js`, `seasonShelves.js`(항아리선반 매핑 함수), `randomPuzzle.js`(타임어택 선반 규칙), `pantryView.js`, `appShell.js`/`pipReaction.js`, i18n 2파일. 단 이 목록은 매핑 문제 해결 *이후* 목록이며, 매핑 설계는 별도 선행 스파이크가 필요하다.
12. **1주 이상 일정에 현실적인가? 줄인다면 무엇을 뺄 것인가?** 비현실적. Phase A에 시즌선반↔항아리선반 매핑 설계라는, 문서에 없던 새 하위 작업이 통째로 추가돼야 한다. 줄인다면: (1) 타임어택 항아리 연동은 V1 제외("타임어택은 능력 미적용" 명시), (2) 시너지는 이미 다음 버전으로 미룸, (3) 배지 능력은 4계열 중 검증하기 쉬운 1~2계열(힌트 절약, 실수 보호)만 먼저 출시하고 나머지는 후속 버전으로.

### 12.4 정리

가장 시급한 선결 과제는 **"시즌 선반(21) ↔ 항아리 선반(11)" 매핑 설계**와 **타임어택의 선반 미소속 문제**다. 이 둘이 해결되지 않으면 §3.1의 핵심 활성화 규칙 자체가 성립하지 않고, 그 위에 얹힌 §4(효과 계열)·§6(경제 시뮬레이션 입력)·시너지가 모두 흔들린다. 경제 시뮬레이션은 §6 표가 아니라 `puzzles.js`의 실제 `reward` 분포를 추출해 다시 세워야 한다. 저장 호환성과 전시/능력 분리는 항아리 쪽은 기존 패턴 재사용이라 상대적으로 안전하지만, 배지 쪽은 신규 UX라 별도 검증이 필요하다.

## 13. Codex 조정안 — Claude 리뷰 반영 (2026-08-11)

Claude의 핵심 반박을 수용한다. 특히 기존 `equippedJars`를 능력 선택으로 바꾸는 안과 퍼즐의 시즌 선반을 항아리 선반에 연결하는 안은 철회한다. 이 절은 앞 절의 충돌하는 설명보다 우선한다.

### 13.1 확정 권고 구조

항아리는 서로 독립된 세 가지 상태를 갖는다.

| 상태 | 역할 | 기존 저장 영향 |
|---|---|---|
| `equippedJars` | 각 팬트리 선반의 외형 | 그대로 유지 |
| `featuredJarId` | 홈 화면 전시 | 그대로 유지 |
| `activeJarId` | 전역 보상 효과 항아리 1개 | 신규, 자동 전환 금지 |

팬트리 상세 화면에는 기존 `선반에 놓기`, `홈에 전시`와 구분되는 `효과 활성화` 동작을 둔다. 최초 능력 시스템 진입 시 Pip이 세 동작의 차이를 설명하고, 효과 슬롯이 비어 있으면 기본 보상만 지급한다. 이미 선택한 외형을 능력으로 자동 승격하지 않는다.

완료 화면은 실제 지급값으로 다음처럼 표시한다.

- `퍼즐 보상 +N` — 해당 퍼즐의 실제 `puzzle.reward` 또는 해당 모드의 라이브 보상 계산값.
- `데일리 보너스 +N` — 적용되는 경우에만 표시.
- `수집품 보너스 +N` — `activeJarId` 효과가 발동한 경우 항아리 아이콘과 함께 표시.
- `총 획득 +N`.

### 13.2 V1 출시 범위 축소

공동 기능 버전의 V1은 기반과 체감이 명확한 최소 범위로 제한한다.

포함:

1. 전역 효과 항아리 1개 선택과 설명 UX.
2. 저작된 일반 퍼즐, 오늘의 그림, 다시 풀기의 경로별 보상 규칙을 코드 감사 후 명시.
3. 항아리 스푼 보너스와 완료 보상 원장/별도 보상 행.
4. 전역 능력 배지 1개 선택.
5. 배지는 정량 검증이 쉬운 최대 2계열만 후보로 둔다. 힌트 절약과 실수 보호도 경제 영향 상한을 통과해야 출시한다.
6. EN/KO, 접근성, 저장 마이그레이션, Android/iOS 동등성.

제외·후속:

- 타임어택 항아리 효과: V1 제외. 생성 퍼즐의 선반 소속을 억지로 만들지 않는다.
- 항아리·배지 시너지: 데이터 구조를 과도하게 선구현하지 않고 후속 버전에서 다시 설계한다.
- 나머지 배지 효과 계열: 실제 이용·경제 결과를 본 뒤 추가한다.
- 21개 시즌 선반 ↔ 11개 항아리 선반 매핑: 전역 효과 구조에서는 필요 없으므로 만들지 않는다.

### 13.3 경제 분석 선행 작업

어떤 보상도 줄이거나 늘리기 전에 라이브 지급 경로를 기계적으로 추출한다.

1. `puzzles.js` 전체의 실제 `puzzle.reward`를 크기·팩·시즌 선반별로 집계한다.
2. 일반 완료, 오늘의 그림, 다시 풀기, 로그인, 스테이지 완료, Spoon Run, 타임어택의 최종 지급 함수와 중복 가능성을 추적한다.
3. `packs.js`, `seasonShelves.js`, `economyConfig.js`의 서로 다른 `stageBonus` 중 실제 호출되는 값을 확정하고 단일 진실 공급원으로 정리할 별도 작업을 만든다.
4. 이 데이터로 현행/A 추가형/B 재배분형/C 상한형을 다시 시뮬레이션한다.
5. 결과가 나오기 전에는 `오늘의 그림 8 → 6`을 포함한 모든 축소 수치를 후보로만 유지한다.

힌트 절약 효과는 직접 지급이 아니어도 스푼 수요를 줄이므로 공급 증가로 환산한다. `전액 보존` 같은 효과는 원칙적으로 V1에서 제외하고, 월간 힌트 관련 스푼 절감량에 별도 상한을 둔다.

### 13.4 오프라인·날짜 조작의 현실적 약속

완전 로컬 앱에서 기기 시계 조작을 완벽히 차단한다고 약속하지 않는다.

- 동일 `completionId` 중복 지급 방지와 보상 원장은 반드시 적용한다.
- 가능한 효과는 날짜보다 완료 횟수·고유 완료 ID 기준 상한을 우선 사용한다.
- 날짜 기반 상한에는 마지막으로 관측한 날짜보다 과거로 돌아간 경우 재추첨하지 않는 완화책을 둔다.
- 서버 검증이 생기기 전에는 이를 부정 방지 기능이 아니라 우발적 중복 방지로 명시한다.

### 15.2 세 가지 결정에 대한 의견

**1) 전역 `activeJarId` 구조 채택 — 찬성.**
§12에서 지적한 구조적 문제를 근본적으로 해소한다. 추가로 확인할 점 하나: `activeJarId`가 미설정일 때 "기본 보상만 지급"(§13.1)이라고 했는데, 이는 곧 능력 시스템에 전혀 참여하지 않는 이용자가 존재함을 뜻한다. §5.1 최초 안내에서 선택을 강요하지 않는다면 이 상태가 영구화될 수 있으므로, 설정에서 다시 안내를 볼 수 있는 경로(기존 `Pip의 가이드` 재사용)를 §13.1에 명시하는 편이 좋다.

**2) 타임어택 보상 자격 강화 — 찬성하되, 별도 트랙으로.**
이 버그는 수집품 기획과 무관하게 존재해온 기존 경제 결함이다(§14.4). 다만 강화 방향에 대한 구체안이 §14에 없어 의견을 보탠다: "완주"를 요구하면 라운드 크기가 커질수록(15×15) 난이도 대비 보상 접근성이 급격히 나빠질 수 있으므로, **완주 또는 진행률 임계치(예: 해당 라운드 전체 채움 칸의 50%↑) 중 하나를 만족** 하는 절충안을 권장한다. 이 결정은 §14.4의 7일/30일 기준선 자체를 바꾸므로, 반드시 §13.3의 경제 시뮬레이션보다 먼저 확정해야 한다 — 순서가 바뀌면 시뮬레이션을 다시 돌려야 한다.

**3) 오늘의 그림 표시 버그 핫픽스 선행 처리 — 강한 찬성.**
이건 수집품 기획과 완전히 독립적인 기존 버그이고(500/500 퍼즐이 잘못된 값을 보여줌), 사용자가 매일 보는 화면이다. 능력 시스템 일정과 묶어둘 이유가 없다 — 다음 배포 사이클에 바로 핫픽스로 분리해 처리할 것을 권장한다.
